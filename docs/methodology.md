# Methodology

How this repository evaluates a RAG system, step by step, in the order a project would
follow. Each step links to the decision record (ADR) that explains its choices and to the
results it produced.

## The system under test

**The system.** AnythingLLM 1.18.0 in Docker, driven only through its developer API,
answering questions over 77 NTSB marine investigation reports (2025–2026, public domain;
[ADR 0003](decisions/0003-corpus-choice.md)).

- **Models:** `qwen3-nothink:8b` (qwen3 8B with thinking off;
  [ADR 0005](decisions/0005-no-thinking.md)) and the `nomic-embed-text` embedder, both on
  Ollama.
- **Mode:** query mode, so the model answers only from retrieved passages
  ([ADR 0014](decisions/0014-query-mode.md)).

**Configs.** Each config is a YAML file in `configs/`, applied idempotently to its own
workspace ([ADR 0002](decisions/0002-provisioning-model.md)). Mutations and weak configs
extend the baseline and change one thing.

**Runs.** Every case runs in a new thread, so no chat history leaks between questions.
Every run writes:

- `traces.jsonl`: question, retrieved passages with scores, answer and latency;
- `manifest.json`: git commit, config hash, pinned image and model digests, and dataset
  and corpus hashes.

## 1. Dataset

**The questions.** 110 questions, each with verbatim evidence quotes from the reports
([ADR 0004](decisions/0004-dataset-size-and-generation.md)). They vary along dimensions
fixed before generation (`data/dimensions.yaml`):

- question type: factual, procedural, causal, comparison, multi-document, unanswerable
  (18%);
- complexity;
- phrasing (close to or paraphrasing the report);
- where the evidence sits in a report;
- whether it crosses a chunk boundary.

**Generation and checks.** The candidates were generated by an LLM from a stratified
plan. Automated checks then ran on each one:

- every quote must be verbatim in AnythingLLM's own parse of the PDF;
- near-duplicate questions are dropped;
- questions that copy most of their evidence's wording are flagged as too easy;
- whether evidence crosses a chunk boundary, and which report section it sits in, are
  measured on the real text;
- per-dimension coverage is compared with the targets.

**Review.** A local review page (`data/review/review.html`) shows each quote in its
report context. Known weak items are listed in `data/candidates/review-notes.md`.

**Split.** The dataset is split, stratified by question type, into **dev (44)** and
**held-out test (66)**, with a fixed seed; the hashes are in `data/splits.json`. Dev is
used for everything that tunes or designs: error analysis, judge prompts and judge
labels. Test is used only for final measurements: the mutations and the eval gate.

## 2. Closed-book baseline

**Why.** Before measuring retrieval, the questions were answered with **no documents**,
to check that a correct answer could not come from the model's memory
([results](results/closed-book-baseline.md); runs in `results/closed-book/`).

**Result.** 3 of 90 answerable questions were answered correctly (95% CI 1–9%), all of
them questions a guess could get right; excluding those, 0 of 78. Correct answers in the
RAG runs therefore reflect retrieval, not prior knowledge.

## 3. Error analysis

**Why first.** It comes before any evaluator, so the evaluators measure failures that
actually happen ([ADR 0006](decisions/0006-error-analysis-setup.md)).

**Traces.** 132 dev traces: the baseline and two deliberately weak configs (fewer
passages, a permissive chat prompt).

**Open coding.** The traces were shown shuffled, with the config hidden. Each one got a
free-text note on the first thing that went wrong (`data/review/traces.html`). If
retrieval failed, the note blames retrieval, not the answer.

**Axial coding.** The notes were grouped into six failure modes
([`failure-taxonomy.md`](failure-taxonomy.md)).

**Finding.** 55 of 66 failures start at retrieval: the passage holding the answer was not
retrieved. The model then either declined (mode A), guessed (B) or gave up on a question
it could half answer (C).

## 4. Evaluators

**The evaluation pyramid:** cheap and certain at the bottom, expensive and uncertain at
the top.

1. **Deterministic checks.** No-context refusals, recognised by exact match on the
   refusal text ([ADR 0014](decisions/0014-query-mode.md)).
2. **Retrieval metrics** ([ADR 0009](decisions/0009-retrieval-metrics.md)): hit rate,
   recall@k and MRR, at document and passage level. Evidence quotes are matched to
   retrieved passages by 6-word shingles. Passage level matters: the baseline finds the
   right report for 96% of test questions but the passage holding the answer for only 69%.
3. **Binary LLM judges** ([ADR 0008](decisions/0008-binary-judges.md)), one per failure
   mode:
   - groundedness;
   - correctness;
   - abstention on unanswerable questions;
   - unnecessary refusal.

   Each is a DeepEval custom metric with its own prompt and three labelled examples. It
   answers Pass or Fail, never a score, and a rule decides instead wherever one can.

**The judge model.** Claude Haiku 5.5, a different model family from the system under
test, run through Claude Code's headless mode
([ADR 0007](decisions/0007-judge-model.md)). Other models plug in through a config file.

## 5. Judge validation

**What it measures.** How often each judge agrees with Pass/Fail labels on real traces
([ADR 0010](decisions/0010-judge-validation.md), [`judges.md`](judges.md)).

**Labels.** 608 marks on 217 dev traces. Two extra weak configs supplied enough failures
for most judges.

**Split.** The labels are split by question into judge-dev and judge-test. Prompts were
improved once on judge-dev, and judge-test was used once.

**Results** (TPR / TNR on judge-test):

| Judge | TPR | TNR | Status |
|---|---|---|---|
| groundedness | 98% | 100% | validated |
| correctness | 95% | 98% | validated |
| refusal | 97% | 100% | only 6 failures to test on |
| abstention | 78% | 100% | 1 failure; **not validated** |

Abstention is not validated because the dev set has too few unanswerable questions that
the system gets wrong.

## 6. Statistics

**Methods** ([ADR 0011](decisions/0011-statistics.md); `src/rag_eval/stats/`,
standard library only, unit-tested against hand-computed values):

- **Pass rates:** Wilson intervals.
- **Other statistics:** percentile bootstrap intervals.
- **Repeated runs:** questions are treated as clusters, so repeats are not counted as
  independent evidence.
- **Comparing two configs on the same questions:** exact McNemar tests and paired
  bootstrap intervals that resample whole questions.
- **Not significant:** reported with the minimum detectable effect, never as "no
  change". With 66 test questions, a comparison detects changes of roughly 11–19 points.

## 7. Mutations

**The idea.** Six deliberate, one-change regressions test whether the evaluation notices
([`mutations.md`](mutations.md)):

- a weaker model;
- fewer retrieved passages;
- a raised similarity threshold;
- a weakened prompt;
- a removed report;
- an edited fact.

**Pre-registration.** The expected effects were committed before any run.

**Result.** 8 of 11 predicted changes were detected, and all 13 "no change" predictions
held.

**What it showed:**

- Retrieval metrics catch the retrieval mutations.
- Groundedness catches the generation mutations.
- Correctness misses the retrieval mutations, because it is already low at baseline.
- The two targeted mutations were uninformative, because the baseline already failed
  their questions.

## 8. Eval gate

`rag-eval gate run` runs the baseline on the test set, scores it, and fails if a gated
metric moves past its threshold ([ADR 0012](decisions/0012-gate-thresholds.md)):

- passage hit;
- groundedness;
- correctness;
- no-context refusals.

**Thresholds.** Each threshold sits below the baseline by a margin set for a 5%
false-alarm rate across the gate.

**Result.** The gate fails all four detected mutations and passes the baseline.

**Where it runs.** It runs manually on a self-hosted runner. Pull-request CI stays fast,
free and LLM-free ([ADR 0013](decisions/0013-ci-and-eval-gate.md)).

## Known limitations

- **Single runs.** The mutation runs and the gate's thresholds use one run per config.
  Three repeats would narrow the intervals and show how consistent repeated runs are.
- **Abstention is not validated.** The dev set needs more unanswerable questions.
- **Targeted mutations need answered questions.** They only test something if the
  baseline answers the targeted questions correctly.
- **Re-embedding is not bit-identical.** Passage scores differ by about ±0.0005 between
  workspaces, which can reorder near-tied passages.
- **No observability platform.** A production system would add one
  ([ADR 0015](decisions/0015-observability-out-of-scope.md)).
